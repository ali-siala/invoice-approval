# Backlog

Non-blocking suggestions that change neither the seed fingerprint nor a policy rule. Newest at the bottom.

- **`requires-python` is wider than what we test.** `pyproject.toml` says `>=3.11`, but some locked packages need Python 3.12 or newer (e.g. numpy 2.5.4), so `uv.lock` contains different, untested versions for 3.11/3.12. Raising it to `>=3.12` or `>=3.13` would match the venv. Needs a SPEC section 9 change, which currently says `>=3.11`.
- **Verify the ZIP lists against an official postal dataset.** The ZIP codes in `ap/seed.py` (`DE_CITIES`) come from memory. The postal-region and bank-region tests are independent, but no single ZIP-to-city pair has been checked against a dataset. If a wrong ZIP turns up, fixing it changes the seed fingerprint.
- **The Dutch VAT checker only knows the company format.** The tests' NL checker accepts company IDs (RSIN, 11-test), which is all the generator creates. It would reject the newer sole-trader format used since 2020 (e.g. python-stdnum's `NL002455799B11`). This only matters if Dutch sole traders are ever added.
- **The project install differs from `uv.lock`.** The venv has the project installed editable via `uv pip`; the lock expects a regular install. With `uv run --no-sync` this never matters; one `uv sync` would align them, but it modifies the venv.
- **Remove the finished Day 5 TODO from CLAUDE.md.** All three items (strip hidden columns, set acting approver, replace the skeleton) are done in `43857f4`; the section now misleads future sessions.
- **Add `-s` to the usual vf-eval command.** With `-d` alone, vf-eval prints only a truncated sample of transcripts and saves nothing, so failed attempts can't be diagnosed afterwards. `-s` writes `results.jsonl` with full completions.
- **Pilot results vary a lot between runs.** The single task scored 1/3 in the first run and 3/3 in the second (same model, same command). Three attempts per task are too few to tell difficulty from noise; use more rollouts before judging task difficulty.
- **The single pilot task may be too easy.** In the Step 1 validity runs both gpt-4.1-mini and gpt-5.6-sol passed it 5/5 (and mini 3/3 in an earlier run). SPEC 7: "A task every model always passes teaches nothing" — consider a harder single task when building the 50.
- **Cost estimates are upper bounds.** vf-eval's `token_usage` has no cached-token breakdown, so estimates assume full input price; most input is a repeated conversation prefix that OpenAI may bill at the cached rate (25 % for gpt-4.1-mini, 10 % for gpt-5.6-sol).
- **Keep the results analysis script.** The per-attempt diff against gold actions used in Step 1 (pass rate, stop reasons, wrong decisions per invoice, token totals) lives only in the session scratchpad; moving it to `scripts/analyze_results.py` would make every future run diagnosable the same way.
- **The gpt-5.6-sol cost estimate for Step 3 is extrapolated.** It scales the pilot's per-tier sol token usage by how much gpt-4.1-mini's usage grew from the pilots to the 50 tasks; measure sol on the first Step 3 slice and re-estimate.
- **Keep the run-merging script.** Step 3 merged each stage's rollouts with its `has_error` re-runs (first R good rollouts per task) using a script that lives only in the session scratchpad; together with the analysis script it belongs in `scripts/` so future runs follow the same rule.
- **The wheel puts `tasks/` and `pyproject.toml` at the top of site-packages.** That is how the verifiers template ships them (`TASKS_PATH` is next to `invoice_approval.py`), but a top-level `tasks` directory can collide with another package's files. Moving it to `ap/tasks/` would avoid that; SPEC section 9 and `TASKS_PATH` would change with it.
- **Docker outputs are owned by root on the host.** The container runs as root, so `docker-outputs/` files need sudo to delete. Running with `--user "$(id -u):$(id -g)"` needs a writable HOME for vf-eval; untested.
- **Dockerfile `CMD` is in shell form.** Docker warns (JSONArgsRecommended) that Ctrl-C may not stop the run cleanly; an exec-form `["sh", "-c", ...]` or a small entry script would fix the warning.
- **The tests need `scripts/make_tasks.py`, which is not in the wheel.** `test_tasks.py` imports it for `coverage` and the edge-case lists, so the Docker image copies `scripts/` next to `tests/`. Moving those helpers into `ap/` (or the tests) would make the tests depend only on the installed package.
- **Two copies of LICENSE.** The repo root and `environments/invoice_approval/licenses/` each hold the Apache-2.0 text (hatch can't include files above the project directory, and `prime env push` uploads only the environment directory, and of its top level only README.md, pyproject.toml, *.py and subdirectories). They are identical now; a test or a symlink check would keep them from drifting.
- **The prime CLI is out of date.** Installed 0.16.0, current 0.19.0 (`prime upgrade`); worth upgrading before `prime env push` in case the push format changed.

## v2 difficulty ideas

- **Reverse charge for the AT/NL suppliers.** Their invoices carry no German VAT (§ 13b UStG); the agent must recognise reverse charge, expect 0 % on the invoice and book input VAT and the tax liability itself. Needs new seed data (fingerprint), new policy rules and ledger lines.
- **Credit notes (Gutschriften).** Negative invoices that reduce a PO's invoiced amount and must be matched to the original invoice; they interact with PO budgets and duplicates. Needs schema, seed, tools and policy changes.
- **Goods receipts / three-way match.** Approve only what was ordered (PO) and actually delivered (Wareneingang); partial deliveries and quantity differences become new hold reasons. Needs a goods-receipt table, line items, tools and policy changes.
- **Invoices as PDF or free text.** The agent first extracts net, VAT, gross, number and PO from a document instead of structured fields; OCR-style noise makes the existing arithmetic and duplicate checks harder. Needs a document tool and generated documents.
- **Pagination in `list_invoices`.** Replace the 200-row limit with pages (cursor or offset) so batch scopes and duplicate checks require several calls; tests the agent's diligence on large inboxes. Tool change only.
